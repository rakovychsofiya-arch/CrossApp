# CrossApp 
Наскрізний проєкт з крос-платформного програмування. 
Предметна область: Склад. 
Сутності: Product (товар), StockBatch (партія), Warehouse (склад), Movement (переміщення).
Призначення: облік залишків товарів по партіях.
## Структура рішення
* `src/Core/` — бібліотека класів (Class Library), що містить спільну логіку, збір системної інформації, а згодом міститиме доменну модель. Не залежить від інших проєктів.
* `src/Cli/` — консольний застосунок, точка входу. Має `ProjectReference` на `Core` і відповідає виключно за взаємодію з користувачем та вивід даних.
## Каталоги для майбутньої логіки в Core:
  * `src/Core/Dto/` — record-типи формату даних (тиждень 3)
  * `src/Core/Domain/` — сутності з поведінкою та інваріантами (тиждень 4)
  * `src/Core/Storage/` — реалізації сховищ (тиждень 5)
## Запуск 
* dotnet build 
* dotnet run --project src/Cli 
* dotnet run --project src/Cli -- --json
* dotnet publish src/Cli -c Release -r win-x64 --self-contained true
* dotnet publish src/Cli -c Release -r win-x64 --self-contained false

## Різниця між Framework-dependent та Self-contained:
* Framework-dependent publish – публікація, що містить код застосунку та його залежності,
але не містить середовища виконання .NET. Тому на комп’ютері користувача має бути
встановлений .NET Runtime відповідної версії.
* Self-contained publish – публікація, до якої входить також .NET Runtime. Такий застосунок
може працювати на комп’ютері без попередньо встановленого .NET, але займає значно
більше місця та створюється для конкретного ідентифікатора платформи (RID), наприклад
win-x64.
## Інваріанти доменної моделі (Product)
1. **Обов'язковість ідентифікатора, SKU та назви:** `Id`, `Sku` та `Name` не можуть бути порожніми або складатися з пробілів (`ArgumentException`).
2. **Канонічність SKU:** SKU автоматично приводиться до верхнього регістру без пробілів (`ToUpperInvariant()`).
3. **Невід'ємний початковий залишок:** Початковий залишок не може бути меншим за 0 при створенні/відновленні з DTO (`ArgumentOutOfRangeException`).
4. **Валідація кількості в операціях:** Кількість приходу (`RegisterArrival`) та видачі (`Issue`) має бути strictly > 0 (`ArgumentOutOfRangeException`).
5. **Захист від перевитрати:** Неможливо видати більше товару, ніж є на складі в даний момент (`InvalidOperationException`).

## Освоєно доменні події, делегати Action/Func, лямбди
* Подія (event) – це обмежений механізм доступу до делегата. Зовнішній код може лише підписатися на подію за допомогою += або відписатися від неї за допомогою -=. Викликати подію може тільки клас, у якому її оголошено. Тому подія безпечніша за публічне поле типу делегата.
* Делегат – це типобезпечне посилання на метод із визначеною сигнатурою.Action – е приймає параметрів і не повертає значення(видавець  повідомляє, що певна подія відбулася, а підписники самостійно визначають реакцію на неї. Подія призначена для сповіщення «щось сталося».)Якщо потрібно отримати значення у відповідь, доцільніше використати метод або делегат Func, а не подію
* Лямбда-вираз – це компактний спосіб оголошення анонімної функції. Якщо лямбда використовує змінні із зовнішньої області видимості, вона утворює замикання (closure). Завдяки цьому обробник події в Cli може, наприклад, змінювати оголошений зовні лічильник.

## Порівняти читабельності з методним синтаксисом:
// 1. Методний синтаксис (Method / Fluent Syntax)
public static IReadOnlyList<GroupSummary> ByUnitFluent(IEnumerable<Product> source) =>
    source.GroupBy(p => p.Unit, StringComparer.OrdinalIgnoreCase)
          .Select(g => new GroupSummary(g.Key, g.Count(), g.Sum(p => p.Quantity)))
          .OrderByDescending(s => s.TotalQuantity)
          .ToList();

// 2. Синтаксис запитів (Query Syntax)
public static IReadOnlyList<GroupSummary> ByUnitQuery(IEnumerable<Product> source) =>
    (from p in source
     group p by p.Unit into g
     orderby g.Sum(x => x.Quantity) descending
     select new GroupSummary(g.Key, g.Count(), g.Sum(x => x.Quantity)))
    .ToList();
Аналіз читабельності та доцільності використання:
* Групування та впровадження змінних (into g):

1. Query Syntax візуально дуже схожий на класичний SQL (from ... group ... by ... into ... orderby ... select), що полегшує сприйняття розробникам з досвідом у реляційних базах даних.

2. У Method Syntax ланцюжок .GroupBy(...).Select(...) вимагає явно працювати з параметром g (типу IGrouping<TKey, TElement>), де лямбда-вирази передаються як аргументи методів розширення.

* Обмеження та зручність лінійного виклику:

1. Method Syntax читається природно зліва направо і зверху вниз (конвеєрний стиль). До нього зручно додавати термінальні оператори, такі як .ToList(), .FirstOrDefault(), .Take(n) без необхідності огортати весь запит у дужки (...).

2. У Query Syntax для матеріалізації (ToList()) або обмеження кількості елементів (Take()) доводиться брати весь вираз у дужки або оголошувати проміжну змінну var query = ....
* Секції сортування та проєкції:

1. У Method Syntax сортування після групування виконується безпосередньо над готовим DTO (s.TotalQuantity), оскільки .Select() йде до .OrderByDescending().

2. У Query Syntax операція orderby стоїть перед select, тому обчислення суми g.Sum(...) доводиться повторювати або використовувати додаткову конструкцію let.
